# Known limitations

- The 2026-10-15 candidate repair is not production acceptance. A green unit run is not a player backpack open/close/relog proof. `ChunkDataEvent.Save` is still not posted. Backpack `SavedData` ordering is unchanged.
- Durable chunk saves keep the dirty generation. They do not reset it to 0. A second completion of an older number must not clear a later mutation. `forget()` still resets a live key to 0. Counters are plain `long` increments; this candidate does not define a wrap protocol past `Long.MAX_VALUE`. Non-holder keys remain in the fixed weak-map stripes until `forget` or collection.
- A store that was attempted and failed stays pending on the chunk map that attempted it. Another dimension's retry cannot drain that set. `flushWorker` joins in-flight stores, then calls `SaveBarrier.awaitStorageFence(this.worker.synchronize(true), deadline)` where `deadline` is `SaveBarrier.deadlineAfter(120_000L)` taken once before that call. That first fence replaces `super.flushWorker()` (`ChunkStorage.flushWorker` is `worker.synchronize(true).join()`). It then joins in-flight stores again, retries that chunk map's pending chunks, and calls `SaveBarrier.awaitStorageFence(this.worker.synchronize(true), deadline)` again for the time left on that same deadline. The two `joinSaveFutures` waits keep their own 120s `managedBlock` budget and are not charged against the deadline. `RegionFile.write` completes the store future without `FileChannel.force`, so the retry future alone is not a durability fence. If that shared budget is already spent, or either fence times out, is interrupted, or gets an exceptional synchronize result, `flushWorker` throws `ChunkSaveBarrierException` (the wait's `TimeoutException`, `InterruptedException`, or `ExecutionException` is the cause) and does not return success. A throw from `synchronize` itself is not caught. A first-fence failure returns before the retry and the second fence; the chunk stays pending on this chunk map. `processUnloads` retries once per tick and does not use that throw, so a live tick is not held for the full budget. The continuation mixin catches only `ChunkSaveBarrierException` around official `ServerChunkCache.save` inside `ServerLevel.save`, so that level's entity `saveAll` or `autoSave` still runs and later dimensions still save. A foreign exception still propagates, including an `IllegalStateException` whose message contains the barrier words. `saveAllChunks` still returns normally so `stopServer` can close levels, and the returned boolean is false when any level hit the barrier. The per-dimension success line is kept for a level that did not fail; the aggregate line is an error. The failed chunk remains unsaved. Player save on the stop path runs before the world save. An I/O completion that blocks on the server thread can still deadlock inside the existing `managedBlock` join; the retry itself is outside `managedBlock`. These mixins apply only while async chunk I/O is enabled. Vanilla `synchronize(true)` snapshots pending region writes and then flushes; a store queued after that snapshot is outside this fence, same as vanilla `flushWorker`.
- `FlushLoopAbandonsDirtyChunkTest.saveLikeCandidate` copies admission policy in a test helper. It is not a mixin execution. `SavePathBytecodeTest` and `SaveContinuationBytecodeTest` disassemble compiled classes and the mapped Forge jar. They do not apply the mixins. A disposable dedicated-server boot, when it is run, is a mixin-apply and readiness check. It is not chest, backpack, or cross-dimension persistence proof.
- Structure-start and structure-reference writes on `ChunkAccess` now advance the dirty generation before they set `unsaved`. That is structure data, not chest or backpack inventory. `setLightCorrect` already goes through `setUnsaved`. The mapped 1.18.2 jar's other direct `unsaved` writes are the `LevelChunk` proto-to-full constructor and `LevelChunk.setBlockState`, which already have hooks.
- Sophisticated Backpacks `BackpackStorage` and Sophisticated Storage `ItemContentsStorage` keep inventories in `SavedData` maps keyed by UUID (staged jars `sophisticatedbackpacks-1.18.2-3.20.3.1063` and `sophisticatedstorage-1.18.2-0.9.8.915`). `ServerLevel.save` writes that data before chunk IO. Losing the chunk item that holds the UUID looks like an empty backpack even when the `SavedData` file is current. Those staged jars contain no `ChunkDataEvent` references. Live jars may differ.
- Isle of Berk Performance Patches 1.3.8 replaces the structure-template cache. That interacts with threaded worldgen template reads, not with container inventory. VonixGuardian 2.1.2 (`9b63124`) can replace a block with an empty block entity during rollback when the mutation has no NBT, and a failed rollback batch stays open. `persistNbt` defaults to true at that commit. Neither peer is modified here.
- Controlled 1.0.7 testing candidate for Minecraft 1.18.2 / Forge 40.3.12 / Java 17. Back up worlds before use.
- Threaded Horizons is a standalone Forge C2ME replacement for this lane. It is not a 1:1 C2ME parity claim, does not bundle a C2ME artifact, and aborts startup if a `c2me` mod ID is already loaded.
- With ModernFix loaded, the optional constructor-time asynchronous structure warmup is intentionally disabled because ModernFix initializes `StrongholdLocationCache` later than `ChunkMap`; structure generation remains available on demand. This is a compatibility guard, not proof of every ModernFix feature interaction.
- With YUNG's Bridges (`yungsbridges`) loaded, FEATURES placement is single-threaded because that mod writes blocks outside the current generation chunk. This does not disable other threaded worldgen statuses and is not a YUNG's Bridges bytecode edit.
- Spark live-viewer protobuf / EventBus failures remain unresolved classification. Threaded Horizons is not claimed as the cause without an A/B proof.
- `optimizeAsyncChunkRequest` is a deliberate safety exclusion on this Forge 1.18.2 replacement. The mixin is hard-skipped and config v3 migrates persisted `true` to `false`. The inherited C2ME 1.18.2 design joins a future that is completed on `mainThreadProcessor`; that join deadlocked `/tp`. No nonblocking replacement that avoids a server-thread join is proven here, so the family stays retired. Re-enabling the key does not restore the path.
- Global biome cache stays disabled, matching upstream C2ME 1.18.2 (`useGlobalBiomeCache` hardcoded false, "DO NOT USE in 1.18"). Sampler identity is not world/source identity; the empty `populateBiomes` mixin is not restored; mixins remain gated off. Thread-local biome cache remains the supported 1.18 path.
- `reduceLockRadius` defaults and migrates `true` on config v4. It is write/lock ownership only. WorldGenRegion `hasChunk`/`getChunk` stay vanilla `firstPos`/`lastPos`. Isle of Berk / Variant Loader biome, sky, and `isWaterBelow` reads fail closed if the chunk is missing. Threaded worldgen stays enabled.
- A matched disposable chunk-generation comparison completed twice: mean debug TPS was 8.95 with Threaded Horizons and 12.62 without it. This is workload-specific evidence, not a universal performance claim.
- Optional Java incubator-vector acceleration is an intentional exclusion on this Forge 1.18.2 / Java 17 toolchain. The `libs/vectorized_algorithms` and `mixin/optimization/vectorizations` source trees are not in the candidate and are not packaged.
- Fabric companion mixins (BetterEnd, BetterNether, Charm, Terra, The Bumblezone) are not present. Missing companions fail closed. The Forge compatibility module loads optional companion mixin JSONs from the classpath and does not reflect into Knot.
- Unreachable duplicate/unused helper types (`fixes.general.threading.IChunkTicketManager`, `AsyncNamedLockDelegateAsyncLock`, `CMETrackingMap`, `DeepCloneable`, `MCUtil`, standalone `common.util.AsyncCombinedLock`) and the Forge-inapplicable `DataFixerUpperClasspathFix` are not in the candidate. Active `common.notickvd.IChunkTicketManager` and `common.threading.scheduler.SchedulingAsyncCombinedLock` remain.
- bStats is not included (not part of the 1.18.2 Fabric reference used here).
- MixinGradle still warns that a few synthetic `ChunkMap` lambda overwrite targets cannot be located during annotation processing. Unload saving uses the remappable `ChunkMap.save` path and joins the store future. The registered `threading.worldgen.MixinThreadedAnvilChunkStorage` hook is a remappable `@Redirect` of `ChunkMap.scheduleChunkGeneration` `thenComposeAsync` (official name; SRG `m_140360_`) that runs the compose immediately instead of overwriting synthetic `lambda$scheduleChunkGeneration$19`. Surrounding implemented mixins still ship in the JAR.
- Enhanced autosave dirty-chunk enqueue uses `MixinChunk` (`ChunkAccess.setUnsaved`) plus `MixinWorldChunk` field writes on `LevelChunk.unsaved` in the proto-to-full constructor and `setBlockState`. Both are listed in `threadedhorizons.mixins.json` and gated by enhanced-autosave mode.
- IO worker NBT-cache drain injects official `IOWorker.storePendingChunk` / `tellStorePending` (mailbox thread). Public `store` / `submitTask` only enqueue work and must not iterate `pendingWrites` on the caller thread.
- Pooled `FeaturePlaceContext` must override the official 1.18.2 accessors `level()` and `random()` (not Yarn `getWorld()`/`getRandom()`). The super constructor stores null finals; vanilla `Feature.place` calls `random()`, so a Yarn-only override NPE'd in `MonsterRoomFeature`.
- Access widening uses SRG member names in `META-INF/accesstransformer.cfg` because ForgeGradle 5 applies AT to the injected SRG-member jar. Unused empty access mixin interfaces were removed from `threadedhorizons.mixins.json`.
- Client mixin config is packaged in the `client` list only. `ThreadedHorizonsMixinConnector` adds that JSON only when `FMLEnvironment.dist == Dist.CLIENT`. Dedicated-server `runtime-g6` never registers those classes. The client plugin also returns false when `LoaderHooks.isClient()` is false. A client-capable launch is outside the disposable dedicated-server harness.
- Retained same-semantics overwrites have mapped-class differential tests in `OfficialOverwriteDifferentialTest`. Behavioral feature-port overwrites are experimental and are not claimed bit-identical to vanilla. See `docs/overwrite-differential.md`.
- `/threadedhorizons status` prints process-local executor queue depths and uncaught/rejected counters for disposable load gates. Those numbers are measurements, not a performance claim.
- Official Forge 40.3.12 `ServerChunkCache.tickChunks` does not invoke `ChunkHolder.getTickingChunkFuture()`. That call is in `isPositionTicking(long)`. The no-tick mixin therefore redirects the remappable `getTickingChunk()` collect-list invoke and `ServerLevel.getAllEntities()`, and does not register a `getTickingChunkFuture` redirect. The 1.18.2 Fabric source left the future redirect commented for the same reason.
- Official `SinglePoolElement.place` does not invoke `Holder.value()`. That call is in `getSettings(Rotation, BoundingBox, boolean)`. The failsafe mixin redirects that `getSettings` invoke, matching the Fabric `createPlacementData` hook.
- Mixin 0.8.5 refuses to load non-mixin classes from a mixin package (`IllegalClassLoadError`). Load/save pairing types live in `common.threading.chunkio`, not as nested mixin records.
- Candidate queue pressure is bounded fail-closed: no-tick actions, scheduler raw/lock/pipeline admissions, storage read/write/flush admissions, save futures, and enhanced-autosave positions reject new work rather than silently dropping it; the owned lighting and I/O worker executors use bounded/awaited shutdown paths. Rejected work remains the caller's explicit failure and is not a universal performance guarantee.
- `InvokingExecutorService` runs submitted work on the calling thread. That is deliberate: `NoiseBasedChunkGenerator.fillFromNoise` / `createBiomes` are redirected over `Util.backgroundExecutor()` so the Threaded Horizons worker keeps the chunk-pipeline slot for the inline work instead of hopping to the vanilla background pool. It is not a memory leak; it does serialize that work onto the worker stack.
- `StacktraceRecorder` stays opt-in (`DebugReducedLockRadius` plus `reduceLockRadius`). Unique retained traces are clamped 16..4096 (default 256). Do not enable it on a live server; equality walks full `StackTraceElement[]` arrays under a global monitor.
- The public repository includes issue tracking for ordinary bugs and compatibility reports. No CurseForge ID or downstream publication is claimed.
